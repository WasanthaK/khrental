# Property enquiries and owner inbox

This is the next website package under the owner-directed listing-to-signing objective. SaaS subscription management remains afterward. The enquiry foundation is in PR #442 and governed schema/registration continuation in PR #443. Public enquiries are not activated by a source deployment.

## Behaviour

A property detail page can link to `/enquire?listingId=<public-reference>&country=LK|BN`. The application retains only that validated public reference and market through normal sign-in. It never accepts a redirect URL or tenant selection from that link. The enquiry screen is isolated from tenant storage, navigation and credential onboarding. Normal login remains the sole credential owner; the enquiry API never issues sessions or grants memberships.

The supported sender is a server-verified, tenantless global seeker. Server session linkage, verified-email evidence, active identity and absence of historical memberships are checked, with authoritative SQL rechecks in each serialized operation. Organization users and tenant administrators cannot impersonate that seeker. This does not change the existing general-signup gate.

New registration now retains the public listing pointer from enquiry → sign-in → seeker registration → verification email → verification in another browser → normal sign-in → the selected enquiry. The server accepts only a validated public listing UUID and LK/BN market as navigation intent, never a redirect URL or tenant selection. The email carries it beside the verification token in the fragment, not in an HTTP path/query. Verification immediately scrubs the fragment and keeps only the safe public pointer for the sign-in link. Tokens/passwords are never put in storage, history state or application logs, and an existing signed-in identity is not automatically replaced. Invalid/expired verification can return to registration with the safe pointer retained.

The sender explicitly consents to sharing their account name, verified email and message with that property's owner workspace. The immutable enquiry records the public reference, server-derived property/workspace, country/title snapshot, contact snapshot, consent version/time and request hash. It contains no uploaded documents, payment information or housing eligibility screening. The existing listing availability/opt-out/country predicate is rerun before a new submission. A successful retry can return the original receipt even if the property subsequently becomes unavailable.

Only one pending/responded enquiry per seeker/listing can exist. A request reference is unique for that seeker; identical retries return the same receipt and changed content returns conflict. Serialized actor and index-range locks, unique indexes, a durable ten-enquiries-per-24-hours limit and bounded payloads protect writes. Deadlock victims receive an explicit retry result rather than an apparent success.

An active workspace administrator reads the inbox under **Property enquiries**, saves a response or closes the enquiry. Server-derived workspace scope and active membership/session are rechecked transactionally. Staff and foreign workspaces are denied. The seeker sees their own receipt and reply, and can withdraw a pending/responded enquiry. Optimistic versions reject stale updates. Status/response events retain their versions and actor; no audit history is erased. Lists are paged in groups of 50.

Replies are stored in the application. **No email notification or confirmed viewing is claimed or sent by this implementation.** Success means the enquiry transaction committed to the owner's inbox. Availability, enquiry, confirmed viewing, reservation, signing and tenancy activation remain separate stages.

## Release boundary

All new gates default OFF. Source changes alone do not activate signup or enquiries. Schema installation uses the protected migration executor.

| Control | Effect |
| --- | --- |
| `PROPERTY_ENQUIRIES_ENABLED=true` | Enables both authenticated enquiry APIs only while the existing public-read/shared-rate readiness gates also allow browsing. Existing single-listing scope, when configured, is enforced for submission. |
| `VITE_PROPERTY_ENQUIRIES_UI_ENABLED=true` | Exposes the application enquiry form and administrator navigation. It grants no API authority. |
| Public capability | The selected eligible listing’s `/api/public-listings/:id/enquiry-status?country=LK|BN` returns only an `enquiriesOpen` boolean. The marketing detail adds its enquiry link only when the explicit public registration mode and all enquiry/seeker UI and API gates are enabled. Hero/category stock imagery is unchanged. |
| Registration scope | The existing normalized-mailbox pilot remains the default. General registration additionally requires `PUBLIC_SIGNUP_RELEASE_MODE=public` and `PUBLIC_SIGNUP_PUBLIC_APPROVED=true`; all existing origin, ingress, verified sender and durable quota controls remain required. |
| Schema | Governed migration `20261028_01_property_enquiries`, exact file `migrations/20261028_01_property_enquiries.sql`. The runner strictly inspects columns, defaults, primary/unique/scoped indexes, filters, trusted non-cascading foreign keys and checks. Installation alone creates no enquiry or public signup access. No request/startup DDL is performed. |

Before activation: apply/verify the governed migration through the protected production workflow using the exact enquiry target, deploy the accepted build, complete controlled authenticated browser acceptance with designated test identities and verify disabled/rollback behaviour. The existing single-mailbox signup pilot and general-signup release remain separate from navigation continuation; no broad registration gate is opened as a side effect. Recheck the actual property and workspace on submission. Do not fabricate live enquiries, create production test users or send mail merely to obtain evidence.

The manual **Property enquiries release controls** workflow defaults to read-only `preflight` and requires the exact accepted serving SHA plus `CHECK-ENQUIRY-READINESS`. It first runs the existing dedicated executor in strict read-only mode against the same database as the serving app, verifying all governed schemas and checksums. The web process separately proves required columns/read-write permissions with zero-row queries, configured mail/origin/limiter and Single revision with min=max=1, without sending mail or creating customer records. SQL definitions remain outside the web identity’s required privileges. Rollback bypasses schema/provider readiness so closure remains possible when those systems are unavailable. `pilot` retains the existing operator-selected mailbox and requires `ENABLE-ENQUIRY-PILOT`. `public` requires `ENABLE-PUBLIC-ENQUIRIES` and a separately approved general-registration release. No email address is supplied through workflow inputs or printed.

Activation checks anonymous API denial, cross-origin signup denial and marketing capability without creating customer data. Failed acceptance closes all new gates and verifies closure. Manual `rollback` requires `CLOSE-PUBLIC-ENQUIRIES`, needs no accepted-build input, and disables the signup, seeker and enquiry gates together. Retain records and audit history; do not drop enquiry tables or mutate occupancy. Existing public browsing and photo gates can remain as independently approved. No extra cloud replica is needed for this package.

## Verification

`tests/property-enquiries.test.js` exercises strict input/consent, safe return destinations, public/private receipt separation, default OFF, anonymous/unverified/foreign-origin denial, configured listing scope, authoritative actor/workspace derivation, owner/staff boundaries and withdrawal-only seeker writes.

`scripts/test-property-enquiries-sqlserver.mjs` executes the exact migration twice, tests strict inspection against missing indexes/untrusted foreign keys, and runs the actual production store on disposable SQL Server: concurrent same-reference submissions, restart replay, conflicting content, duplicate open enquiries, foreign workspace denial, response/version conflicts, durable audit history, withdrawal, opt-out/country/reservation denial, durable quota and session/membership revocation. The general governed-migration proof independently executes the new migration twice and verifies its exact metadata and empty initial tables. Disposable containers are removed on completion and never use production configuration.

`scripts/test-property-enquiries-browser.mjs` exercises the real enquiry, login and owner-inbox components against isolated synthetic API fixtures: selected listing through login, required consent, failure/retry, saved enquiry, owner reply, seeker refresh, mobile width, withdrawal and disabled UI. External requests are blocked. It also covers registration, verification in another browser and normal sign-in back to the selected listing using synthetic transport. This fixture proof is distinct from production acceptance and does not prove real email delivery. `tests/public-signup-release-policy.test.js` checks pilot/public approval and anonymous listing capability boundaries; the marketing browser proof follows the actual capability link without contacting production.

The disposable SQL proof also uses a separate user with SELECT/INSERT/UPDATE access but denied VIEW DEFINITION: strict metadata inspection correctly fails under that identity, the runtime access proof succeeds, and revoking audit INSERT makes the runtime proof fail without creating records. Fresh strict schema/ledger acceptance remains mandatory in the release workflow under the dedicated executor.

The existing authentication/authorization regressions and production build also run. The local runtime prevents Chrome's socket creation; actual browser/SQL acceptance runs in GitHub's disposable jobs. Record successful run/head references in current canonical status before marking acceptance complete. Historical failed fixtures remain failures; later corrected proof supersedes their readiness implication.
